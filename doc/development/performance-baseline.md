# 性能测量口径与预期规模（阶段 1 基线）

> 阶段 1 尚无业务数据流，本文档先固定"预期规模"与"测量口径"，后续阶段
> （采集入库、检索、创作、发布、统计）的验收均按此口径测量并记录到对应
> `phase-0N.md`，避免各阶段自行编造数字。

## 预期素材规模（单租户）

| 维度 | 预期量级 | 说明 |
| --- | --- | --- |
| 公众号来源 | ≤ 50 个 | 采集来源账号上限 |
| 每来源每次采集新文章 | ≤ 20 篇 | 单次采集任务产物 |
| 每日入库素材 | ≤ 2,000 篇 | 全部来源单日合计 |
| 素材总量（一年） | ≤ 500,000 篇 | 正文平均 3,000 字（约 6KB/篇），约 3GB 正文 |
| 正文修订 | 每素材 ≤ 10 版 | 旧版本保留但不参与默认检索 |
| chunk（向量） | 每素材约 5 段 | 检索阶段按 500 字分块估算，年增约 250 万向量 |
| 并发用户 | ≤ 30 同时在线 | 内部运营工具，写并发通常 ≤ 5 |
| 采集/创作异步任务 | 同时 ≤ 20 个 worker 任务 | Redis + Celery（阶段 2 起） |

## 测量口径

1. **延迟**：统一记录 p50 / p95 / p99，样本为服务端处理时间（不含客户端网络）。
   列表类接口验收线：p95 ≤ 500ms（≤ 50 万行、命中索引）；检索接口验收线在阶段 4 实测后回填。
2. **并发**：用 `k6`/`wrk` 或 pytest-benchmark 对关键端点按 30 虚拟用户压测 5 分钟，
   记录 RPS、错误率（应 < 0.1% 业务错误，不含故意越权的 4xx）。
3. **数据规模**：每个阶段验收时记录 `pg_stat_user_tables` 的行数与表体积
   （`pg_total_relation_size`），写入对应 phase 文档，验证预期规模假设。
4. **异步任务**：记录任务入队→完成时长分布与失败重试次数，口径在阶段 2 定义后回填。
5. **不比较未受控变量**：不在同一口径下比较不同机器/不同数据量级的结果；
   每次测量记录当时的 PostgreSQL 版本、数据量、机器配置。
