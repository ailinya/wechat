# 异步执行与恢复

## Purpose

保证采集、解析、向量生成、创作、同步和发布等后台动作具有可靠受理、可查询进度及可恢复结果。用户或下游系统在网络、消息服务或执行进程异常后仍能识别原任务，重复投递不得造成重复业务产物或绕过人工控制。

## ADDED Requirements

### Requirement: 持久化任务状态
系统 SHALL 持久保存任务类型、业务对象、阶段、进度、起止时间、重试次数和失败原因，区分业务状态与运行状态；进程重启 MUST 不丢失已受理任务记录。

#### Scenario: 重启后查询任务
- **WHEN** 后台进程重启，用户查询此前受理的任务
- **THEN** 系统返回原任务及已保存状态，不因临时结果过期而丢失业务历史

### Requirement: 可靠受理与可恢复投递
系统 MUST 确保已确认受理的业务动作不会因消息服务暂时不可用而丢失；业务受理失败时不得产生可执行的孤立后台动作。

#### Scenario: 消息服务中断
- **WHEN** 业务动作已持久受理但消息服务暂不可用，随后服务恢复
- **THEN** 原任务能够继续投递执行，用户无需创建第二个业务对象

#### Scenario: 受理事务失败
- **WHEN** 任务受理因数据校验或事务失败而回滚
- **THEN** 不执行该动作，也不向用户返回可靠受理成功

### Requirement: 重复执行不重复副作用
系统 MUST 在请求重发、消息重投及并发消费者场景下维持同一业务动作的幂等性，不重复创建素材、文章、批次槽位或已成功的外部发布。

#### Scenario: 执行完成后消息重投
- **WHEN** 同一任务完成业务写入后再次收到重复消息
- **THEN** 系统恢复原结果，不再次产生相同业务产物

### Requirement: 明确失败与有限重试
系统 SHALL 为可重试失败保留原因与尝试记录，重试次数达到约定上限后停止自动重试；条件不满足和已取消 MUST 不显示为执行成功。

#### Scenario: 外部服务持续失败
- **WHEN** 同一任务因外部服务错误达到配置的自动重试上限
- **THEN** 任务显示失败及原因，保留各次尝试，不无限循环或伪造成功

### Requirement: 安全恢复与取消边界
支持取消的任务 SHALL 明确允许取消的状态，成功取消后 MUST 不提交新的业务产物；进程中断后的恢复 MUST 检查既有结果和外部状态，不能盲目重做未知结果的动作。

#### Scenario: 创作取消与完成竞争
- **WHEN** 用户取消创作任务而任务可能同时提交结果
- **THEN** 系统只接受一个一致的终态；若取消成功则不新增产物，若已完成则返回不可取消及原结果

#### Scenario: 恢复未知发布结果
- **WHEN** 发布进程中断且无法判断外部平台是否已接受发布
- **THEN** 系统保留待核对状态，按发布核对规则处理，不直接重新发布
